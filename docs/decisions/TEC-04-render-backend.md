## 1. 맥락

- R0 분석(feeltech 4.12)은 헤드리스 Chromium으로 프로덕션 빌드 C5S10(적 204)을 돌렸다. 결과는 DPR1 p50 16.7 ms, DPR2 p50 33.3 ms(30 fps), 롱태스크 0이었고, 이를 래스터(필레이트) 한계로 보았다. 같은 문서가 "헤드리스 소프트웨어 래스터일 가능성이 있어 실기 GPU로 재확인이 필요하다"고 적어 두었다.
- 백로그는 Canvas2D 아틀라스 경로를 실기 Electron에서 재고, 미달이면 WebGL2 스프라이트 배처로 바꾸라고 한다. 게이트는 1440×900 DPR2에서 p95 16.7 ms 이하이고, 렌더 스케일 1.5까지 허용한다.
- TEC-03으로 캐릭터 스프라이트가 들어와 있다. 그래서 같은 장면을 스프라이트 경로와 벡터 경로로 비교할 수 있다.

## 2. 방법

- 실제 엔진과 렌더러(`GameEngine` + `WorldRenderer`)를 제품과 같은 조건의 Electron 창에서 돌린다. 콘텐츠 1440×900, sandbox, 같은 CSP를 쓰고, 데이터 폴더는 임시로 만든다.
- DPR은 Chromium `--force-device-scale-factor`로 1과 2를 강제한다. 렌더 스케일은 엔진에 새로 넣은 `setRenderScale`로 정한다. 백킹 스토어는 CSS px × min(DPR, 스케일, 2)이고, 기본값 2는 기존 동작과 같다.
- 장면
  - **stress**: 백로그의 고정 부하다. Ch1 4역할 적 204(정지, 186이 화면 안), 적탄 240, 파티클 520, 데미지 숫자 160을 매 시뮬레이션 스텝 보충한다.
  - **game**: 실제 스테이지를 시계 85% 지점에서 시작한다. 스폰, 보스, 위험지형이 있고 스킬 5종 빌드를 쓴다. 신 모드에서 원을 그리며 움직인다. C1S10은 스프라이트로, C5S10은 벡터로 그린다(Ch5 팩은 아직 없다).
- 지표
  - animation frame 간격: p50/p95/p99/최대, 그리고 34.2 ms 초과 수(60 Hz vsync를 두 번 이상 놓친 프레임).
  - 프레임 안 메인 스레드 시간(시뮬레이션 + 렌더)과 렌더 시간.
  - 롱태스크 수.
  - 워밍업 4초(게임 장면 20초) 뒤 12초를 잰다.
- **제한 해제 측정**: `--disable-frame-rate-limit --disable-gpu-vsync`로 vsync에 가려진 여유를 본다. 이때 간격은 GPU를 포함한 프레임 전체 비용의 대리 지표다.
- 기기: MacBook Pro 16"(Apple M1 Pro, GPU 16코어, 메모리 16 GB), macOS 26.6.1, 외장 4K 60 Hz 모니터(DPR 1), Electron 43.0.0.

## 4. 해석

- **놓친 프레임이 없다.** 12개 구성 모두 34.2 ms를 넘은 프레임이 0이다. 가장 긴 간격은 21.9 ms였다. 2880×1800(DPR2)에서도 60 fps를 유지한다.
- **p95 17.0~17.7 ms는 vsync 흔들림이다.** 60 Hz 디스플레이의 프레임 타이밍이 16.7 ms 앞뒤로 흔들려 생긴 값이다. 프레임을 실제로 놓치면 33 ms 근처가 찍힌다. 그래서 게이트 문구 "p95 ≤ 16.7 ms"를 vsync에 묶인 측정에 그대로 적용하면 어떤 장면도 통과할 수 없다(§5 D-3).
- **여유가 크다.** 제한을 풀면 stress 장면이 DPR2에서 p50 2.0 ms, p95 3.4 ms다. 60 Hz 예산의 약 1/5이다. DPR1과 DPR2의 차이도 거의 없어, 이 기기에서는 필레이트 한계가 보이지 않는다. R0의 DPR2 33.3 ms는 재현되지 않는다. 헤드리스 Chromium의 소프트웨어 래스터 결과로 보인다.
- **스프라이트와 벡터는 비용이 비슷하다.** 차이가 측정 오차 안이다(렌더 p95 2.6 대 2.7 ms, 제한 해제 p95 3.4 대 3.1 ms). ImageBitmap blit은 이 장면에서 벡터보다 느리지 않다. 스케일 없는 정수 좌표 blit만 이득이라는 R0 우려(visuals 7.3)는 이 기기에서는 문제가 되지 않는다.
- **메인 스레드는 시뮬레이션이 더 크다.** 프레임 안 작업 p95는 3.3~5.0 ms다. 가장 큰 C5S10(적 195) 5.0 ms 가운데 렌더는 2.3 ms이고 나머지는 시뮬레이션이다. 적 행동·분리(SYS-02)가 들어오면 시뮬레이션 비용이 먼저 늘어난다.

## 6. 남은 확인 [확인]

- **Intel Mac(x64)**: 지원 사양 가운데 GPU가 가장 약하므로 팀이 측정한다. 방법은 `npm run bench:render`다. 제한 해제 p95가 11 ms를 넘으면 렌더 스케일 기본값을 1.5로 낮추는 안을 검토한다.
- **120 Hz 화면**: 내장 ProMotion 화면에서 한 번 더 잰다. 이번 측정은 외장 60 Hz 모니터였다.
- **GPU 시간 교차 확인**: GPU 시간은 페이지 안에서 직접 잴 수 없다. 제한 해제 간격은 대리 지표이므로, Instruments(Metal System Trace)로 한 번 교차 확인하면 좋다.
- **품질 게이트 수치 정리**: `docs/QUALITY_GATES.md`의 성능 목표(프레임 p95 20 ms 이하)와 이 항목의 게이트(16.7 ms)가 다르다. D-3을 확정할 때 한 문구로 맞춘다.

## 7. R1 재판정 (2026-10-01)

R1 끝(f05b83e)의 Ch1 실제 에셋으로 같은 12개 구성을 다시 쟀다. 적·보스·처치·데칼·픽업·환경(지면·소품·경계) 스프라이트와 데미지 숫자 글리프가 모두 들어간 상태다. 같은 기기와 같은 방법이다.

**찾은 문제: 지면 패턴 채우기.** 스프라이트 경로가 크게 느려져 있었다.

- 프레임 안 작업은 5 ms 아래인데 간격이 180 ms였다. 비용이 메인 스레드 밖, 캔버스 래스터에 있다는 뜻이다.
- 기능을 하나씩 끄며 좁혔다.
  - 데미지 숫자를 끄거나, ART-05의 지면(반복 패턴 채우기)을 끄면 16.7 ms로 돌아왔다.
  - 둘을 함께 켤 때만 느렸다. 적 스프라이트, 타격 별, 소품은 영향이 없었다.
- 원인은 같은 프레임에서 화면 전체를 이미지 패턴으로 채우고 작은 이미지를 수백 번 찍는 조합이다. Chromium 캔버스가 이 조합에서 크게 뒤처진다. 글리프 시트를 ImageBitmap으로 바꾸거나 채우기 뒤에 fillStyle을 되돌려도 그대로였다.
- **고친 것:** 지면을 패턴 채우기 대신 타일 이미지로 한 장씩 찍는다(화면에 6~16장, `WorldRenderer.drawGround`). 이음새는 이웃 타일과 0.5유닛 겹쳐 가린다.

**판정**
- D-3 게이트를 모두 통과한다.
  - 놓친 vsync 프레임(25 ms 초과)이 0이다. p99가 가장 커도 18.7 ms다.
  - 프레임 안 작업 p95는 가장 커도 6.2 ms다(C5S10 DPR2, 기준 8 ms).
  - 제한 해제 p95는 3.4~3.6 ms로 R0(3.1~3.4 ms)와 거의 같다. 기준은 11 ms다.
- stress 스프라이트의 p95 18.5~18.6 ms는 vsync 흔들림이다. 16.7 ms 앞뒤로 흔들린 간격이며, 한 번 놓친 프레임(약 33 ms)은 없다.

- D-1(Canvas2D 유지)을 확정한다.
- **남은 것:** R2에서 챕터마다 같은 벤치를 스프라이트로 다시 잰다(R2 챕터 게이트). ART-08에서 벤치 페이지가 장면의 챕터 팩을 불러오게 한다.
- **[확인]** 성능 게이트는 지금 수동이다. 이번 문제는 기능 테스트와 시각 게이트를 모두 통과했다. 벤치의 `stress` 한 구성을 릴리스 게이트에 넣을지 정한다(약 30초).

## 8. 재현

```
npm run bench:render                  # 12개 구성, 약 6분. artifacts/performance/render-bench.json
BENCH_ONLY=stress npm run bench:render # 이름이 맞는 구성만
BENCH_SECONDS=30 npm run bench:render  # 측정 창 변경(BENCH_WARMUP도 가능)
```

벤치는 창을 띄우고 화면 맨 앞에 있어야 정확하다. 측정 중에는 다른 무거운 작업을 멈춘다.
